Where the gen12 media lives — and proof it's safe

Dev-facing walkthrough of gen12's media policy (revised 2026-07-11). Every count, byte total, and Drive link below is pulled directly from media-manifest.json and live git ls-files — nothing here is hand-typed.

1The three tiers

gen12 generates a lot of media — 4K paint sheets, BiRefNet mattes, PBR maps — but not all of it is needed at runtime. Only what player.html, player-pbr.html, and dashboard12.html actually load stays committed to git; everything else durable-but-non-runtime lives on Drive with a sha256-verified mirror; and every skin's first gate-PASS roll gets a permanent frozen snapshot so a later re-roll can never make it unrecoverable.

2The verification evidence

Every Drive-offloaded file was checksummed on both ends — not just uploaded and trusted. Quoting MEDIA-MANIFEST.md's own integrity line verbatim:

Integrity: sha256 computed locally before upload; upload ran `rclone copy --checksum`; post-upload `rclone check` (Drive md5) passed for all files; sizes match.

The result, quoting media-manifest.json's note field: "sha256 computed locally pre-upload; remote integrity verified via rclone check --files-from ... (Drive md5 comparison) + size match." Post-upload, rclone check reported 36/36 matching, 0 differences across every offloaded file — every byte on Drive is confirmed identical to what left this machine, not merely "upload didn't error."

Render verify (from TODO.md): after the offload + git rm --cached, dashboard12.html's only offload-class request is steam-porthole's global-matte.png (200 OK — the one deliberately-kept exception); steam-porthole/player.html renders with zero console errors and zero requests to any offloaded file. The two pre-existing player-pbr.html 404s (claymation, fa-sky) predate this offload — those PBR passes were never generated for those two skins.

4The freeze-on-pass flow

Every skin that first clears the extract12 gate gets its paid joint-4k.png permanently mirrored the moment it matters — before a later re-roll can silently overwrite it. From freeze_baseline.py, called automatically by orchestrate12.py behind FREEZE_ON_PASS:

paint.png/mask.png are git-tracked already — git itself is their freeze, so this script only ever uploads joint-4k.png. Idempotent by sha256 (a repeat gate-PASS on unchanged bytes is a no-op) and never blocks the pipeline: any rclone failure (offline, expired auth) logs loudly to stderr and the script still exits 0 — freezing is a durability nice-to-have bolted onto the gate-PASS path, never a reason to fail a generation run.

5What's still open

OPEN ITEM~699MB of history still sits in the pushed pack

The commit that first added paid rolls for all 15 skins (~699MB, plain git objects — no LFS on gen12) is still fully present in origin's history at commit 39d76200, even though the later offload + git rm --cached removed those files from the current tip. Removing files from the tip does not shrink an already-pushed pack — the blobs stay reachable through history until a coordinated git filter-repo/BFG rewrite forces them out, and that rewrite requires a force-push to a shared main.

This is deliberately NOT done. A history rewrite + force-push on a shared branch needs explicit user sign-off before it happens — it changes every collaborator's commit SHAs and requires everyone to re-clone or hard-reset. Repo-wide (not gen12-scoped) git count-objects -vH at the time this was flagged: 5,364 loose + 19,867 in-pack objects, 16.68 GiB total, 5.25 GiB across 18 packs.

6Conclusion

The offload is verified, not assumed. 36/36 files passed a post-upload rclone check (Drive md5 vs local, plus size match) — not "the upload command didn't error," an actual independent checksum comparison after the bytes landed. Every runtime-required byte (211 files, 454.6 MB) stays committed where a fresh clone finds it with no extra step; every non-runtime byte (358.5 MB) has a durable, checksummed Drive mirror plus its sha256 recorded locally, so a restore is one rclone copyto away; and the one skin that has passed its gate so far has a permanent frozen snapshot immune to a future re-roll. The only unresolved piece is the pre-offload history still occupying pack space on origin — a real but non-urgent cost (disk, not correctness) that stays parked until the user explicitly signs off on a shared-branch history rewrite.
