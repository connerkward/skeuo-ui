4 — Hypothesis tests

(a) art↔visualizer identity SWAP — refuted as a clean label-swap. Detected visualizer is never closer to album_art's template slot than to its own (0/32 gens) — so visualizer isn't being mislabeled as album_art. What is true: detected album_art sits closer to visualizer's template slot than its own in 24/32 gens, because album_art gets dragged toward wherever the visualizer-like second window ends up. It's a one-sided pull, not a mutual swap.

(b) model promotes album_art to a hero position — refuted. "Hero" would mean moving further toward prominence (template already puts album_art at the very top, y≈0.11). Instead album_art moves down and away from that position in the vast majority of large-drift cases (mean dy strongly positive) — toward wherever the model decided to put its matched *pair* of display windows, which is frequently the bottom of the composition, not a more prominent top spot.

(c) mask blob agrees with template, but extract12's region-refit moved it (pipeline bug) — refuted. Independent check: BiRefNet-adjacent guide-key blob centroid in each gen's own mask.png channel vs extract12's regions.device refit centre. Wherever a blob was isolable, the two agree within ~10–20px of each other and both disagree with the template by hundreds/thousands of px in the same direction (e.g. steam-porthole album_art: mask centroid frac [0.747, 0.645] vs refit centre [0.728, 0.645]; wmp-quicksilver: mask [0.717, 0.625] vs refit [0.697, 0.623]). extract12 is faithfully reporting what the model actually painted — this is paint-driven, not detector-driven, consistent with the prior bisect chain (892bf045, 448d8f87).

ANSWER

Systematic template weakness, expressed probabilistically — not random, not a clean identity-swap

  • Not random variance: the same failure mode (album_art + visualizer losing their fixed stacked order) recurs across 24/32 templated gens spanning both layout archetypes (vpod and hcapsule), multiple themes, multiple seeds, and both serving paths (fal / Vertex) — visually confirmed by direct crop inspection, not just the distance metric.
  • Not per-skin deterministic either: the SAME skin re-rolled lands on both branches — e.g. steam-porthole's frozen mainline roll is side-by-side (FAIL), but 3/4 fresh servingbisect re-rolls of steam-porthole are correctly stacked; fallout-pipboy's frozen roll is order-reversed, but 2/4 fresh re-rolls stack correctly. So a re-roll has a real (~60-70%) chance of fixing any one failing skin, but that's resampling from a distribution that's still wrong ~30-45% of the time — it doesn't fix the underlying weakness for the NEXT skin/seed.
  • Root cause, visually confirmed: the template puts album_art directly above visualizer with a near-hairline gap (~2% of frame height in the vpod archetype — the two "dark recessed glass, no coloured frame" windows are template-adjacent and visually near-identical). The model has its own strong compositional prior for a paired "twin display" element and frequently re-composes it as side-by-side (9/32) or vertical-order-reversed (5/32) rather than obeying the template's specific stacked position — even in PASSING gens (fa-pod's mainline roll is a clean side-by-side pair, it just stays close enough in Euclidean template-distance to clear the 650px gate).
  • hcapsule's bigger gap (~13% of DEV_H) mostly avoids this (ps1-crunchy: small drift, correct order) but not always (wmp-quicksilver: side-by-side, FAIL) — gap size alone doesn't fully explain it; the "no coloured frame" identical-look prompt clause for both windows likely compounds it.
The one fix: redesign the album_art/visualizer sub-layout in genskin.py's _vpod/_hcapsule layout archetypes (fix-generalizable-rule — pipeline fix, not a per-skin patch). Two complementary moves, both required:
  1. Widen the template gap between album_art and visualizer substantially (vpod's current gap is ~2% of frame height — effectively touching). A template that already reads as two visually distinct elements is far less likely to get merged/reordered by the model than one that reads as a single ambiguous strip.
  2. Add an explicit relative-position prompt clause for these two controls specifically — none currently exists (genskin.py has zero ABOVE/BELOW/stacked language for album_art/visualizer; the current prompt relies entirely on the guide blueprint's geometry, which the model treats as a loose suggestion for this pair). Something like: "album_art sits DIRECTLY ABOVE visualizer with a clear gap — never side-by-side, never reversed."
Re-rolling the 3 currently-failing skins is a reasonable stopgap given the ~60-70% single-roll success rate shown by the servingbisect fresh gens, but it does not fix the ~30-45% expected miss rate for every future templated skin — the template/prompt change is the generalizable fix.
